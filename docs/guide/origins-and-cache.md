# 源站与缓存

网站「源站」与「缓存」页签：源站池与源站组、健康检查、回源协议与连接、S3 源站、缓存规则、缓存键、PURGE 方法、压缩，集群缓存区，以及刷新与预热。

## 概念

| 术语 | 定义 |
| --- | --- |
| 源站池 | 一个网站的全部源站，以及负载均衡、健康检查、超时和长连接设置。每个网站一个源站池。 |
| 主源 / 备用源 | 未打开「备用」的源站为主源，按负载均衡策略接收流量；备用源只在全部主源不可用时接收流量。 |
| 源站组 | 源站上的分组标签，空为默认组。请求默认只发往默认组；「源站覆盖」规则可把请求发往其他组。 |
| 缓存规则 | 按列表顺序匹配的规则，决定响应是否缓存及缓存多久。 |
| 缓存键 | 区分缓存对象的请求属性组合，对网站的全部缓存规则生效。 |
| 缓存代数 | 网站级计数器（API 字段 `cacheGeneration`），属于缓存键的一部分。整站刷新是节点任务，不改变该计数器。 |
| 缓存标签 | 源站在响应头 `Cache-Tag` 中给出的标签；按标签刷新只刷新带该标签的缓存对象。 |
| 缓存区 | 节点存放缓存对象的磁盘目录与其索引。每个集群一个设置，节点可单独覆盖容量。 |

### 保存与生效

| 项目 | 行为 |
| --- | --- |
| 发布 | 保存后控制台为网站所在集群发布新配置版本（原因 `site_updated`）；编译结果与当前版本相同时不产生新版本。刷新、预热任务与缓存区不经过此流程 |
| 提示 | 「已保存」，下方显示「生效中 {current}/{total}」，集群的在线节点都应用后变为「已生效」；集群没有在线节点时为「没有在线节点」 |
| 审计 | `site.update`，元数据 `changed` 列出保存的部分（`origins`、`originSettings`、`cacheRules`、`cacheSettings`、`contentSettings`）；PURGE 密钥只记为已修改 |
| 节点能力 | 依赖节点能力的开关或字段在集群有活动节点不支持时不可用，卡片显示「集群中有节点不支持」（缓存规则为「集群中有节点不支持规则扩展」）；已开启的仍可关闭，已保存的值仍可修改。服务账号与后台任务发布的配置需要集群活动节点缺少的能力时被拒绝（`NODE_CAPABILITY_REQUIRED`） |

## 配置源站

1. 打开 **网站**，选择网站，进入「源站」页签。
2. 在「源站」卡片中修改已有源站，或点击「添加源站」。
3. 填写「源站地址」「端口」「回源协议」「权重」；按需填写「回源 Host」「SNI」（仅 HTTPS）「源站组」，选择「PROXY protocol」，按需打开「备用」「S3 签名」。在「源站地址」中粘贴或输入 `https://origin.example.com:8443` 这样的 URL 时，协议与端口填入各自的字段。
4. 点击卡片底部的「保存」。
5. 验证：提示变为「已生效」后，经节点访问网站：

   ```bash
   curl -sI -H 'Host: www.example.com' http://<节点 IP>/
   ```

   返回源站的状态码；有流量后，源站旁显示「正常」。

### 流量路径

「源站」页签顶部的「流量路径」卡片按已保存的配置画出请求的去向。

| 节点 | 内容 |
| --- | --- |
| 访客 | 起点 |
| 集群 | 网站所在集群的名称与「{applied}/{total} 已应用」（运行网站最新版本的在线节点数 / 在线节点数）；颜色表示网站已生效、生效中或已停用 |
| 源站组 | 组名（空组显示「默认组」）与负载均衡方式；「回源 HTTP 版本」为 HTTP/2 时附「HTTP/2」 |
| 源站 | 地址与 `协议:端口`；备用源站标「备用」 |

| 连线 | 内容 |
| --- | --- |
| 组到主源 | 同一组有多个主源且负载均衡不是一致性哈希时，标出权重占比 |
| 组到备用源 | 标「故障切换」 |
| 异常 | 有节点报告源站不可用时，源站与它的连线显示为异常；全部在线节点都报告不可用时颜色加深 |

源站健康每 10 秒刷新一次。

### 源站字段

| 字段 | API 字段 | 取值 | 默认值 | 作用 |
| --- | --- | --- | --- | --- |
| 源站地址 | `address` | 主机名或 IPv4/IPv6 字面量，不含端口和方括号，最长 253 字符 | 无 | 回源目标，受[源站地址限制](#源站地址限制)约束 |
| 端口 | `port` | 1–65535 | HTTP 80，HTTPS 443 | 回源端口；切换协议时，空端口或另一协议的默认端口随之改为新协议的默认端口 |
| 回源协议 | `scheme` | HTTP / HTTPS | HTTP | 节点到源站的协议 |
| 权重 | `weight` | 1–100 | 1 | 三种负载均衡策略共用的权重 |
| 回源 Host | `hostHeader` | 主机名或 IP，可带端口；IPv6 带端口时写成 `[2001:db8::1]:8443`，不带端口时不加方括号；最长 259 字节 | 空（「跟随请求」） | 发往源站的 `Host`。空：访问者请求的 Host（小写、去端口）；S3 源站为源站地址，端口不是 80（HTTP）或 443（HTTPS）时带端口 |
| SNI | `sni` | 主机名，最长 253 字符，保存为小写 | 空（「跟随回源 Host」） | 仅 HTTPS 显示。空：回源 Host（去端口），再为空时用源站地址；源站地址为 IP 字面量时不发送 SNI |
| 源站组 | `group` | 1–32 个小写字母、数字、`_` 或 `-` | 空（「默认组」） | 见[源站组](#源站组) |
| PROXY protocol | `proxyProtocolVersion` | 关闭 / v1 / v2（API：0 / 1 / 2） | 关闭 | 每条回源连接先发送访问者连接的地址，见 [PROXY protocol](#proxy-protocol)；打开「S3 签名」后不可用。选择 v1 或 v2 后显示「源站须支持 PROXY protocol」 |
| 备用 | `backup` | 开 / 关 | 关 | 设为备用源 |
| S3 签名 | `s3` | 开 / 关（API：对象或 `null`） | 关 | 用 AWS Signature V4 签名回源请求，见 [S3 兼容对象存储](#s3-兼容对象存储) |

| 项目 | 行为 |
| --- | --- |
| 数量 | 每个网站 1–32 个源站，至少一个在默认组；只剩一个源站时不能移除 |
| 顺序 | 按卡片中的顺序保存 |
| 源站 ID | 保存时协议、地址与端口都不变的源站保留原 ID（健康状态与回源质量的记录随之保留）；其他源站按新源站创建 |
| 健康状态 | 每个源站编号旁显示「正常」「{down}/{total} 个节点不可用」或「无在线节点」，下方显示最后一次错误与每个节点的结果，每 10 秒刷新；有节点报告不可用的源站左侧显示红色边线 |

### 源站池设置

「源站池设置」卡片单独保存。卡片中自上而下为：负载均衡、回源 HTTP 版本与三个开关，「回源 TLS」「会话保持」「被动健康检查」「回源重试」「主动健康检查」「超时（秒）」「回源长连接」各组。

| 字段 | API 字段 | 取值 | 默认值 | 作用 |
| --- | --- | --- | --- | --- |
| 负载均衡 | `policy` | 加权随机 / 轮询 / 一致性哈希（`weighted_random` / `round_robin` / `consistent_hash`） | 加权随机 | 主源之间的选择策略，见[负载均衡与重试](#负载均衡与重试) |
| 回源 HTTP 版本 | `protocol` | HTTP/1.1 / HTTP/2（`http1` / `http2`） | HTTP/1.1 | 节点请求源站用的 HTTP 版本，见 [HTTP/2 与 gRPC](#http2-与-grpc) |
| 校验源站证书 | `tlsVerify` | 开 / 关 | 开 | 校验 HTTPS 源站证书，见[回源 TLS](#回源-tls)；关闭时「信任」恢复为系统 CA |
| WebSocket | `websocket` | 开 / 关 | 开 | 透传 WebSocket 升级请求，见 [WebSocket](#websocket) |
| gRPC | `grpc` | 开 / 关 | 关 | 以 HTTP/2 端到端转发 gRPC 请求；「回源 HTTP 版本」为 HTTP/2 时才能打开，改回 HTTP/1.1 时自动关闭。打开后显示「gRPC 请求不经过 OWASP CRS」 |
| 回源 TLS：信任 | `tlsTrust` | 系统 CA / Origin CA（`system` / `originCa`） | 系统 CA | 校验时信任的 CA；关闭「校验源站证书」时不可用。Origin CA 见[源站保护](https.md#源站保护) |
| 回源 TLS：出示客户端证书 | `clientCertificate` | 开 / 关 | 关 | 回源时出示集群的回源客户端证书，见[源站保护](https.md#源站保护) |
| 会话保持：启用 | `sessionAffinity.enabled` | 开 / 关 | 关 | 见[会话保持](#会话保持) |
| 会话保持：Cookie 有效期（秒） | `sessionAffinity.ttlSeconds` | 60–604800 | 3600 | 同上 |
| 被动健康检查：失败次数 | `maxFails` | 1–100 | 3 | 连续失败达到该值后标记源站不可用 |
| 被动健康检查：恢复时间（秒） | `recoverySeconds` | 1–3600 | 30 | 标记不可用后多久再次尝试 |
| 回源重试：尝试次数 | `tries` | 1–5 | 3 | 每个请求最多尝试的源站数 |
| 回源重试：源站返回 502 / 503 / 504 时重试 | `statusRetry` | 开 / 关 | 开 | 关闭后源站的 502/503/504 响应直接返回访问者，连接失败与超时仍重试 |
| 主动健康检查 | `activeHealthCheck` | 见[主动健康检查](#主动健康检查) | 关闭 | |
| 超时（秒）：连接 | `connectTimeoutMs` | 0.1–120（API：100–120000 毫秒） | 10 | 建立连接的超时 |
| 超时（秒）：发送 | `sendTimeoutMs` | 0.1–3600（API：100–3600000 毫秒） | 60 | 向源站发送请求的超时 |
| 超时（秒）：读取 | `readTimeoutMs` | 0.1–3600（API：100–3600000 毫秒） | 60 | 两次读取响应数据之间的超时；不作用于已升级的 WebSocket 连接 |
| 回源长连接：启用 | `keepalive` | 开 / 关 | 开 | 复用到源站的连接 |
| 回源长连接：空闲时间（秒） | `keepaliveIdleSeconds` | 1–3600 | 60 | 空闲连接保留时间；关闭长连接时不可用 |
| 回源长连接：最大请求数 | `keepaliveMaxRequests` | 1–100000 | 1000 | 单个连接处理的最大请求数；关闭长连接时不可用 |

| 字段 | 节点能力 |
| --- | --- |
| 回源 HTTP 版本为 HTTP/2、gRPC | `origin-http2-v1` |
| 信任 Origin CA | `origin-ca-v1` |
| 出示客户端证书 | `origin-mtls-v1` |
| 会话保持 | `session-affinity-v1` |
| 主动健康检查 | `active-health-v1`；gRPC 探测另需 `active-health-grpc-v1` |
| 尝试次数不是 3，或关闭「源站返回 502 / 503 / 504 时重试」 | `site-content-v1` |

配置阶段的规则可按请求覆盖三项超时与「WebSocket」，见[覆盖设置](rules.md#覆盖设置)。

### 负载均衡与重试

| 策略 | 行为 |
| --- | --- |
| 加权随机 | 按权重随机选择；重试按权重顺序选择未尝试过的源站 |
| 轮询 | 平滑加权轮询（与 nginx 相同的算法），每个 worker 独立计数 |
| 一致性哈希 | 按原始请求 URI（路径加查询）哈希，同一 URI 固定到同一源站；一个源站不可用时只有映射到它的 URI 改选其他源站 |

| 项目 | 行为 |
| --- | --- |
| 尝试次数 | 每个请求最多尝试「尝试次数」个源站（默认 3） |
| 触发重试 | 连接失败、超时（含 TLS 握手失败）；打开「源站返回 502 / 503 / 504 时重试」时还包括源站返回 502/503/504 |
| 不重试 | `POST`、`LOCK`、`PATCH` 请求发出后不重试；`PUT`、`DELETE` 会重试 |
| 重试范围 | 只在当前可用的一组源站内：有健康主源时只在健康主源之间；全部主源不可用时使用备用源；不在同一请求内切换 HTTP 与 HTTPS 源站 |
| 剔除 | 域名解析失败、解析结果全部为特殊用途地址或缺少 S3 凭据的源站在尝试前剔除，实际尝试次数可能少于「尝试次数」 |

### 被动健康检查

不发送探测请求；健康状态只由真实流量判断。打开主动健康检查后两者合并，见[合并规则](#合并规则)。

| 项目 | 行为 |
| --- | --- |
| 计为失败 | 连接失败、超时、源站返回 502/503/504（关闭状态码重试时同样计入）、域名解析失败、解析结果全部为特殊用途地址、缺少 S3 凭据、校验证书时节点缺少 CA 文件 |
| 清零 | 其他任何响应清零失败计数 |
| 标记不可用 | 连续失败达到「失败次数」后，在「恢复时间（秒）」内不被选中 |
| 恢复 | 恢复时间结束后重新接收流量；一次成功即恢复健康，再失败一次立即重新标记为不可用 |
| 失败开放 | 全部源站不可用时仍按主源、备用源的顺序尝试 |
| 共享范围 | 同一节点的所有 worker 共享健康状态；各节点独立判断 |
| 上报 | 节点随心跳上报（默认每 15 秒）；「源站」卡片显示「{down}/{total} 个节点不可用」和最后一次错误，每个节点的结果标出来源「被动」或「主动」 |

| 错误码 | 界面显示 |
| --- | --- |
| `connect_failed` | 无法连接源站 |
| `timeout` | 源站响应超时 |
| `upstream_status` | 源站返回 HTTP {status}（被动检查：仅源站自身返回 502/503/504；主动检查：不在期望范围内的状态码） |
| `dns_failed` | 无法解析 {host} |
| `address_forbidden` | {address} 是特殊用途地址，不在源站地址允许清单内 |
| `tls_failed` | TLS 握手或证书校验失败 |
| `grpc_status` | gRPC 健康检查返回 gRPC 状态码 {status}（主动检查，gRPC 探测；`5` 为源站没有该服务） |
| `grpc_not_serving` | gRPC 健康检查结果为 {status}（主动检查，gRPC 探测；`NOT_SERVING`、`UNKNOWN` 等） |

错误码需要节点 proto v0.2.1 及以上；其他错误和更早的节点显示节点上报的原文。

### 主动健康检查

1. 在「源站」页签的「源站池设置」卡片中，打开「主动健康检查」的「启用」。
2. 选择「探测方式」：HTTP 时填写「路径」，选择「方法」；gRPC 时按需填写「gRPC 服务」。按需修改其他字段。
3. 点击卡片底部的「保存」。
4. 验证：令一个源站的检查路径返回期望范围以外的状态码（gRPC：令该服务报告 `NOT_SERVING`）；约「间隔（秒）×不健康阈值」秒后，该源站显示「{down}/{total} 个节点不可用」，节点结果标为「主动」，请求不再发往它。

| 字段 | API 字段（`activeHealthCheck.`） | 取值 | 默认值 | 作用 |
| --- | --- | --- | --- | --- |
| 启用 | `enabled` | 开 / 关 | 关 | 关闭时保留填写的值 |
| 探测方式 | `type` | HTTP / gRPC（`http` / `grpc`） | HTTP | gRPC 调用源站的 `grpc.health.v1.Health/Check`，见 [gRPC 探测](#grpc-探测) |
| gRPC 服务 | `grpcService` | 0–255 个可打印 ASCII 字符，不含空格 | 空（「整个服务器」） | 仅 gRPC：Check 请求中的服务名 |
| 方法 | `method` | GET / HEAD | GET | 仅 HTTP：探测请求的方法 |
| 路径 | `path` | 以 `/` 开头，可带查询，1–1024 个可打印 ASCII 字符，不含空格 | `/` | 仅 HTTP：探测请求的路径 |
| Host | `host` | 主机名，最长 253 字符 | 空（「跟随回源 Host」） | 探测请求的 `Host`；为空时用源站的「回源 Host」，再为空时用源站地址 |
| 状态码下限 / 状态码上限 | `expectedStatusMin` / `expectedStatusMax` | 100–599，下限不大于上限 | 200 / 399 | 仅 HTTP：范围内的状态码为成功 |
| 间隔（秒） | `intervalSeconds` | 5–300 | 30 | 同一源站两次探测的间隔 |
| 超时（秒） | `timeoutSeconds` | 1–60，不超过间隔 | 5 | 单次探测的时限，超时记为失败 |
| 健康阈值 | `healthyThreshold` | 1–10 | 2 | 连续成功多少次后恢复健康 |
| 不健康阈值 | `unhealthyThreshold` | 1–10 | 3 | 连续失败多少次后标记不健康 |

| 项目 | 行为 |
| --- | --- |
| 执行者 | 每个节点的 agent 分别探测网站的每个源站；探测请求数随节点数增加，间隔不宜过短 |
| 地址策略 | 与回源相同：解析结果中特殊用途地址（不在允许清单内）被丢弃，只连接校验过的地址；没有可用地址时记为失败（`dns_failed`、`address_forbidden`） |
| 请求 | 协议和端口与源站相同；HTTPS 发送 SNI（源站的 SNI、回源 Host 或地址），「校验源站证书」打开时校验证书；「回源 HTTP 版本」为 HTTP/2 时以 HTTP/2 探测；不跟随跳转；最多读取 64 KiB 响应体 |
| 失败 | 连接失败、超时、TLS 失败、状态码不在范围内；错误码与被动检查相同 |
| PROXY protocol | 源站要求 PROXY protocol 时，探测连接先发送 `PROXY UNKNOWN`（v1）或 LOCAL 命令（v2），不带访问者地址 |
| 初始状态 | 健康；节点启动或配置变化后的第一次探测在一个间隔内随机开始 |
| 不探测 | S3 兼容源站（未签名的探测不代表签名请求）、地址字面量被禁止的源站 |
| 节点停止探测 | 数据面的「主动不健康」标记在最长间隔的 3 倍（至少 90 秒）后失效，回到只有被动检查 |
| 上报 | 不健康或有连续失败的源站随心跳上报，来源「主动」；「源站不可用」告警同时使用两种来源 |
| 节点要求 | 节点能力 `active-health-v1`；集群有活动节点不支持时「启用」不可用（「集群中有节点不支持」） |

#### gRPC 探测

| 项目 | 行为 |
| --- | --- |
| 请求 | `POST /grpc.health.v1.Health/Check`，请求体为 `HealthCheckRequest`（「gRPC 服务」为空时服务名为空，即整个服务器）；`Host` 与 HTTPS 的 SNI、证书校验同 HTTP 探测 |
| 协议 | 总以 HTTP/2 探测，与「回源 HTTP 版本」无关：HTTP 源站以 h2c（prior knowledge）直连，HTTPS 源站经 ALPN 协商 `h2`，协商不出时记为失败 |
| 成功 | HTTP 200、`grpc-status` 为 0 且回答 `SERVING` |
| 失败 | 连接失败、超时、TLS 失败；HTTP 状态码不是 200（`upstream_status`）；`grpc-status` 不为 0（`grpc_status`，源站没有该服务时为 5）；回答不是 `SERVING`（`grpc_not_serving`） |
| 阈值与上报 | 间隔、超时、阈值、合并规则与上报和 HTTP 探测相同；「路径」「方法」「状态码下限」「状态码上限」不显示，保存的值保留但不使用 |
| 节点要求 | 节点能力 `active-health-grpc-v1`（另需 `active-health-v1`）；集群有活动节点不支持时「探测方式」不能改为 gRPC |

#### 合并规则

| 主动检查 | 被动检查 | 结果 |
| --- | --- | --- |
| 未开启 | 任意 | 与没有主动检查时相同 |
| 不健康 | 任意 | 不参与选择 |
| 健康 | 标记不可用 | 不参与选择，直到被动检查的恢复时间结束 |
| 健康 | 可用 | 参与选择 |

全部源站都不可用时仍按主源、备用源的顺序尝试（失败开放）。

### 回源质量

「源站」页签的「回源质量」卡片显示所选时间范围内每个源站的回源情况，数据来自节点每分钟上报的计数，不受访问日志采样率影响。所选范围内没有回源时显示「暂无回源」。

| 列 / 项目 | 说明 |
| --- | --- |
| 源站 | 地址；备用源站标「备用」，非默认组的源站标组名 |
| 回源请求 | 发往该源站的每次尝试；重试再计一次。包含缓存锁、后台更新与预热的回源，不含缓存命中与主动健康检查 |
| 错误率 | （无法连接 + 超时 + TLS 失败 + 无效回答 + 5xx）÷ 回源请求；鼠标停在错误率上显示「无法连接 {connect} · 超时 {timeout} · TLS 失败 {tls} · 无效回答 {invalid} · 5xx {server}」。无法连接、超时、TLS 失败与被动健康检查的判断相同；无效回答是源站回的不是 HTTP/1.x 响应；5xx 包含 500 |
| 耗时 p50 / 耗时 p95 | 有回答的尝试到收到响应头的时间（不含传输正文）。节点按 10、25、50、100、250、500 毫秒与 1、2.5、5、10 秒分档计数，百分位在档内线性估算，超过 10 秒显示「> 10 秒」 |
| 折线 | 「回源耗时 p95」与「错误率」：每个源站随时间的变化；没有回源的时间段不画点 |
| 时间范围 | 「过去 1 小时」「过去 6 小时」「过去 24 小时」（默认）「过去 7 天」「过去 30 天」，与「统计」页签共用（URL 参数 `range`）；7 天与 30 天读按小时汇总的数据。删除后重新添加的源站从新的记录开始 |
| 部分节点 | 集群有活动节点缺少节点能力 `origin-stats-v1`（节点 1.4.0 之前）时显示「集群中有节点版本过低，不上报回源统计」，数字只含上报的节点 |

### 会话保持

1. 在「源站池设置」卡片中打开「会话保持」的「启用」，按需修改「Cookie 有效期（秒）」。
2. 点击「保存」。
3. 验证：第一次回源的响应带 `Set-Cookie: __ew_affinity=…`；带着这个 Cookie 的后续请求都发往同一个源站。

| 项目 | 行为 |
| --- | --- |
| Cookie | `__ew_affinity`，`Path=/; HttpOnly; SameSite=Lax`，HTTPS 时加 `Secure`；值为源站 ID、到期时间与签名；`Max-Age` 为「Cookie 有效期（秒）」 |
| 签名 | HMAC-SHA256，使用集群的挑战密钥（与[挑战](challenges.md)的通行凭证相同），集群内任一节点都能验证；密钥轮换后上一把仍可验证 |
| 签发 | 只在回源的响应上签发（缓存命中不签发）；已有有效 Cookie 且剩余有效期超过一半时不重复签发 |
| 改选 | Cookie 指向的源站不可用（主动或被动检查）、已删除，或不在当前接收流量的一层（主源健康时的备用源）时，按负载均衡改选并重新签发；篡改或过期的 Cookie 同样处理 |
| 重试 | 被固定的源站本次请求失败时仍按重试规则换源站，响应改为固定到实际应答的源站 |
| 关闭时 | 保留「Cookie 有效期（秒）」 |
| 节点要求 | 节点能力 `session-affinity-v1` 与 `challenge-v1`；集群有活动节点不支持时「启用」不可用 |

### 回源 TLS

| 项目 | 行为 |
| --- | --- |
| 证书校验 | 「校验源站证书」打开时，节点用 CA 文件校验 HTTPS 源站证书，证书须覆盖本次尝试的 SNI；重试换源站时按新源站的 SNI 校验 |
| CA 文件 | 默认使用第一个存在的文件：`/etc/ssl/certs/ca-certificates.crt`、`/etc/pki/tls/certs/ca-bundle.crt`、`/etc/ssl/ca-bundle.pem`、`/etc/ssl/cert.pem`；节点可用 `--trusted-ca <绝对路径>` 指定 |
| IP 源站 | 按 IP 配置的 HTTPS 源站须填写证书覆盖的「SNI」或「回源 Host」 |
| 关闭校验 | 只影响该网站；不校验的 HTTPS 连接不进入连接池 |
| Origin CA | 「信任」为 Origin CA 时只信任控制台的 Origin CA，拒绝它吊销的证书；节点的 CA 文件不参与。需要先打开「校验源站证书」（`ORIGIN_TLS_TRUST_REQUIRES_VERIFY`）、网站没有 S3 源站（`ORIGIN_CA_S3`）、Origin CA 已创建（`ORIGIN_CA_NOT_FOUND`） |
| 客户端证书 | 「出示客户端证书」打开时，HTTPS 源站要求客户端证书就出示集群的证书（S3 源站除外），HTTP/1.1、HTTP/2、gRPC 与主动健康检查相同。需要回源客户端 CA 已创建（`ORIGIN_CLIENT_CA_NOT_FOUND`）；集群没有有效证书时保存时签发 |
| 连接池 | 按源站 IP、端口、SNI、信任方式和客户端证书区分；校验过的连接不会被需要校验其他名称、信任其他 CA 或出示其他证书的请求复用 |

### WebSocket

WebSocket 升级请求（`Upgrade: websocket`）默认透传，不经过缓存。关闭「WebSocket」后，升级请求返回 403，响应头 `X-Edgeweir-Error: websocket-disabled`。

升级后的连接空闲 3600 秒（网站「访问控制」页签的[空闲超时](access-control.md#websocket-来源与空闲超时)，60–86400 秒）后关闭，网站的「发送」「读取」超时不作用于它；配置阶段规则的「回源发送超时」「回源读取超时」优先于它，见[覆盖设置](rules.md#覆盖设置)。只接受指定来源的升级请求见 [WebSocket 来源](access-control.md#websocket-来源与空闲超时)。

### HTTP/2 与 gRPC

1. 在「源站」页签的「源站池设置」卡片中，把「回源 HTTP 版本」改为「HTTP/2」；需要转发 gRPC 时再打开「gRPC」。
2. 点击卡片底部的「保存」。
3. 验证：提示变为「已生效」后，源站访问日志里的请求为 HTTP/2。gRPC 网站可经节点调用，例如：

   ```bash
   grpcurl -authority grpc.example.com <节点 IP>:443 list
   ```

| 项目 | 行为 |
| --- | --- |
| 协商 | HTTPS 源站经 TLS ALPN 协商 `h2`；HTTP 源站以 HTTP/2 直连（prior knowledge，h2c）。源站不支持 HTTP/2 时回源失败，不回退到 HTTP/1.1 |
| 回源 Host | 以 `host` 请求头发送，不发送 `:authority` |
| 缓存与规则 | 与 HTTP/1.1 相同：边缘缓存、回源规则、超时与重试照常生效 |
| WebSocket | 升级请求仍以 HTTP/1.1 回源；只支持 HTTP/2 的源站不能使用 WebSocket |
| 连接池 | HTTP/1.1、HTTP/2 与 gRPC 的回源连接各自复用，互不混用 |
| 主动健康检查 | HTTP 探测以 HTTP/2 发送；HTTPS 源站协商不出 `h2` 时记为失败。gRPC 服务常对普通请求返回 415，把「探测方式」改为 gRPC，见 [gRPC 探测](#grpc-探测) |
| 节点要求 | 节点能力 `origin-http2-v1`；集群有活动节点不支持时「回源 HTTP 版本」与「gRPC」不可用（「集群中有节点不支持」） |

打开「gRPC」后，`Content-Type` 为 `application/grpc` 的请求（含 `+proto`、`+json` 等后缀或参数）经 HTTP/2 端到端转发：

| 项目 | 行为 |
| --- | --- |
| 客户端连接 | gRPC 客户端须以 HTTP/2 连接节点：HTTPS 端口对该网站的域名启用 HTTP/2（「HTTPS」页签关闭 HTTP/2 时也是）；集群有网站打开 gRPC 时，HTTP 端口也接受 h2c，未打开 gRPC 的网站的域名对 h2c 请求返回 421 |
| 流式 | 请求与响应双向逐帧转发，trailers（`grpc-status`、`grpc-message`）原样传回；客户端流与双向流可用 |
| 缓存与压缩 | 不缓存，节点不压缩 |
| 请求体 | 不限大小 |
| OWASP CRS | 不检查 gRPC 请求：ModSecurity 读完整个请求体后才转发，流式调用无法完成。`Content-Type` 由客户端决定，网站的其他接口也能以该类型绕过 CRS；源站的 gRPC 接口与其他接口不分开时，把 gRPC 放到单独的网站 |
| 规则与防护 | 封禁、规则与限速照常生效；gRPC 客户端无法完成人机验证，需要时用「允许」规则豁免 gRPC 路径 |
| 超时 | 「读取」超时是两次收到数据之间的上限；长时间没有消息的流需调大「读取」超时（最多 3600 秒），或用配置规则按路径覆盖 |
| gRPC-Web | `application/grpc-web` 不属于 gRPC 请求，按普通 HTTP 请求处理 |

### PROXY protocol

源站需要访问者的地址而不读 `X-Real-IP`、`X-Forwarded-For` 时（如 HAProxy、带 `proxy_protocol` 的 nginx、邮件或其他按连接记录地址的服务），节点在每条回源连接开头发送 PROXY protocol 头。

1. 在「源站」卡片中，把源站的「PROXY protocol」改为 v1 或 v2，与源站接收的版本一致。
2. 点击卡片底部的「保存」。
3. 验证：提示变为「已生效」后经节点访问网站，源站记录的客户端地址为访问者的地址，目标地址为访问者连接的节点地址与端口。

| 项目 | 行为 |
| --- | --- |
| 地址 | 源地址与端口为访问者连接的地址（按集群的[访客 IP](../deploy/nodes.md#访客-ip) 取得，与 `X-Real-IP` 相同）；目标为访问者连接的节点地址与端口（节点前有 PROXY protocol 时为该头中的目标）。地址不是 IP 时发送 `PROXY UNKNOWN`（v1）或 LOCAL 命令（v2） |
| 发送时机 | 每条新回源连接一次，在 TLS 握手与请求之前；HTTP/1.1、HTTP/2、gRPC 与 WebSocket 都发送 |
| 连接复用 | 回源连接只被同一访问者连接上的请求复用，且每个 nginx worker 各有连接池：同一访问者连接的请求可能由不同 worker 处理，最多各开一条回源连接。访问者连接多时回源连接数相应增加 |
| 写入失败 | 记为无法连接（`connect_failed`），按重试规则换源站；回源质量照常计数 |
| 主动健康检查 | 探测连接发送 `PROXY UNKNOWN`（v1）或 LOCAL 命令（v2） |
| 不同源站 | 每个源站单独设置；同一源站组内可以混用 |
| S3 源站 | 不可用（`ORIGIN_PROXY_PROTOCOL_S3`，「S3 源站不支持 PROXY protocol」） |
| 源站不接收 | 源站不读 PROXY 头时把它当作请求的一部分，通常回 400 或断开连接 |
| 节点要求 | 节点能力 `origin-proxy-protocol-v1`（`edgeweir-openresty` 1.31.1.1-3 及以上）；集群有活动节点不支持时，「PROXY protocol」为关闭的源站不能改为 v1 或 v2（「集群中有节点不支持」） |

L4 应用的 PROXY protocol 见 [L4](l4.md#proxy-protocol)。

### 源站组

源站的「源站组」把网站的源站分成几组，留空为默认组。没有命中「源站覆盖」规则的请求只发往默认组。

1. 在「源站」卡片中为源站填写「源站组」，例如 `api`，点击「保存」。至少保留一个源站在默认组，否则卡片显示「至少保留一个默认组源站」，不能保存。
2. 在「规则」页签的「回源」阶段点击「添加规则」，填写表达式，例如 `starts_with(http.request.uri.path, "/api/")`；「动作」选择「源站覆盖」，「源站组」选择 `api`，按需填写「回源 Host」「SNI」「端口」，打开「启用」（新规则默认停用），点击「保存」。字段见[动作字段](rules.md#动作字段)。
3. 验证：请求 `/api/` 下的路径，源站日志显示请求到达 `api` 组的源站；其他路径仍到达默认组。

| 项目 | 行为 |
| --- | --- |
| 组内选择 | 负载均衡、主源与备用源、重试、健康检查与会话保持都只在选中的组内进行；轮询状态与一致性哈希按组计算 |
| 覆盖 | 规则的「端口」作用于组内每个源站；「回源 Host」「SNI」替换源站自己的设置，「回源 Host」不影响 S3 源站；SNI 为空时照常跟随回源 Host |
| 缓存键 | 不含源站组。按缓存键以外的条件（例如请求头）选择组时，不同组的响应共用缓存对象 |
| 引用检查 | 规则只能选择网站已有的组；移除仍被规则选择的组时，保存提示「规则无效」（`RULE_INVALID`） |
| 全局规则 | 全局规则的「源站覆盖」不能选择源站组，只覆盖回源 Host、SNI 与端口 |
| 节点要求 | `rules-v2`；集群有活动节点不支持时，「源站」卡片显示「集群中有节点不支持」，默认组的源站不能移出默认组，已有的源站组仍可修改或清空 |

## 请求体上限

网站「源站」页签的「请求体上限」卡片单独保存。

| 字段 | API 字段 | 取值 | 默认值 | 作用 |
| --- | --- | --- | --- | --- |
| 上限（MiB） | `contentSettings.requestBodyLimit`（字节） | 0–10240，可带小数（API：0–10737418240） | 100（API：104857600） | 请求体超过上限时返回 413；0 不限制 |

| 项目 | 行为 |
| --- | --- |
| 判断依据 | 带 `Content-Length` 的请求按它判断；不带的请求体（HTTP/1.1 分块上传、HTTP/2 与 HTTP/3 中没有 `Content-Length` 的请求）由节点先读完，按实际大小判断。都在规则之后判断；413 带 `X-Edgeweir-Error: body-too-large`，页面按 413 → 「其他 4xx」→ 内置页查找，见[错误页](error-pages.md) |
| 读取上限 | 节点读取请求体时以节点全局上限为界：集群内所有已启用网站与规则上限的最大值（任一为 0 时不限），超过时同样返回 413 |
| 节点版本 | 不带 `Content-Length` 的请求体按网站上限判断需要节点 1.1.0 及以上；更早的节点只按节点全局上限约束它们 |
| 按请求覆盖 | 配置阶段规则的「请求体上限（MiB）」覆盖网站上限，见[覆盖设置](rules.md#覆盖设置) |
| gRPC | 不检查 |
| 节点要求 | 不是 100 MiB 时需要节点能力 `site-content-v1`；集群有活动节点不支持且上限为 100 MiB 时卡片不可用 |

规则读取请求体的上限（`contentSettings.rulesBodyLimit`）在「规则」页签设置，见[规则](rules.md)。

## 源站地址限制

源站不能指向特殊用途地址。

| 类别 | 地址段 |
| --- | --- |
| IPv4 | `0.0.0.0/8`、`10.0.0.0/8`、`100.64.0.0/10`、`127.0.0.0/8`、`169.254.0.0/16`、`172.16.0.0/12`、`192.0.0.0/24`、`192.0.2.0/24`、`192.168.0.0/16`、`198.18.0.0/15`、`198.51.100.0/24`、`203.0.113.0/24`、`224.0.0.0/4`、`240.0.0.0/4` |
| IPv6 | `::/128`、`::1/128`、`100::/64`、`2001:db8::/32`、`fc00::/7`、`fe80::/10`、`ff00::/8`；IPv4 映射地址（`::ffff:0:0/96`）和 NAT64 地址（`64:ff9b::/96`）按内嵌的 IPv4 地址判断 |
| 主机名 | `localhost` 和 `*.localhost` 始终拒绝；`127.1`、`2130706433`、`0x7f000001` 这类最后一段为数字的名称不是合法地址 |

| 检查点 | 行为 |
| --- | --- |
| 控制台保存 | IP 字面量落在上述地址段时拒绝保存（`ORIGIN_ADDRESS_FORBIDDEN`） |
| 节点回源 | 对配置中的地址和每次 DNS 解析结果执行同一清单；解析结果中的特殊用途地址被丢弃，全部被丢弃时记为回源失败（`address_forbidden`） |
| 允许清单 | 在 **系统设置 → 源站地址允许清单** 放行地址段，保存后向所有集群发布，见[源站地址允许清单](system.md#源站地址允许清单)；`localhost` 不能放行 |
| 回环检测 | 节点向源站发送 `CDN-Loop`（RFC 8586）；收到带本节点标识的请求时返回 508（`X-Edgeweir-Error: loop-detected`） |

## S3 兼容对象存储

在源站上打开「S3 签名」后填写以下字段。「预设」按服务商填入源站地址模板与区域示例，把地址中 `<region>` 这类尖括号部分换成自己的值；预设只填表单，不保存。

| --- | --- | --- | --- | --- |
| 预设 | 无 | 自定义 / 下表中的服务商 | 自定义 | 填入源站地址与区域 |
| 区域 | `region` | 以字母或数字开头的字母、数字、`-`，最长 64 字符，保存为小写 | 无 | SigV4 签名区域，例如 `us-east-1` |
| Bucket | `bucket` | 3–63 个小写字母、数字、`.`、`-`，首尾为字母或数字 | 空（「可选」） | 填写后使用路径式地址 `/<bucket>/<key>`；源站地址已包含 bucket 时（如 `assets.s3.us-east-1.amazonaws.com`）留空 |
| Access Key ID | `accessKeyId` | 1–128 字符 | 无 | 访问密钥 ID |
| Secret Key | `secretAccessKey` | 1–256 字符 | 无 | 只写；同一 Access Key ID 已保存过时显示「已保存，留空不修改」。新的 Access Key ID 必须填写（`S3_SECRET_REQUIRED`） |

| 项目 | 行为 |
| --- | --- |
| 签名 | AWS Signature V4，载荷不签名（`UNSIGNED-PAYLOAD`）；删除访问者请求中的 `x-amz-*` 头 |
| 方法 | 只转发 `GET` 和 `HEAD`；没有其他非 S3 源站可接收时，其他方法返回 405（`Allow: GET, HEAD`，`X-Edgeweir-Error: method-not-allowed`） |
| 查询字符串 | 访问者的查询字符串不转发给对象存储 |
| 密钥存储 | 按网站与 Access Key ID 保存一份 Secret Key，用主密钥信封加密入库；不再被任何源站使用的密钥在保存时删除。只经节点通道（mTLS）下发；节点保存在状态目录的 `credentials.json`（0600），用于控制台不可达时重启 |
| 不可用的设置 | PROXY protocol（`ORIGIN_PROXY_PROTOCOL_S3`）；「信任」为 Origin CA（`ORIGIN_CA_S3`）；不出示回源客户端证书；不做主动健康检查 |

## 配置缓存规则

1. 打开 **网站**，选择网站，进入「缓存」页签。
2. 在「缓存规则」卡片中点击「添加规则」；或点击「静态资源」添加静态资源规则模板（见下表）。
3. 在「构建器」中填写「路径前缀」「后缀」；或切换到「高级」，在「表达式」中填写条件，见[请求条件](#请求条件)。
4. 选择「动作」，填写「缓存时间（秒）」，按需填写「浏览器 TTL（秒）」；只对静态资源关闭「遵循源站」。
5. 需要更多条件时点击「更多条件」（按钮上的数字为已填写的项数），填写「精确路径」（仅构建器）「状态码」「最小（KB）」「最大（KB）」「过期后后台更新（秒）」「回源出错时用旧缓存（秒）」，或打开「缓存带 Authorization 头的请求」「缓存带 Set-Cookie 的响应」。
6. 拖动规则左侧的手柄调整顺序。
7. 点击「保存」。
8. 验证：同一 URL 请求两次，第二次命中缓存：

   ```bash
   curl -sI -H 'Host: www.example.com' http://<节点 IP>/static/app.js | grep -i x-cache
   ```

   第二次输出 `X-Cache: HIT`。

| 模板 | 路径前缀 | 后缀 | 缓存时间（秒） | 遵循源站 |
| --- | --- | --- | --- | --- |
| 添加规则 | `/` | 空 | 3600 | 开 |
| 静态资源 | 空 | `css`、`js`、`mjs`、`map`、`png`、`jpg`、`jpeg`、`gif`、`webp`、`avif`、`svg`、`ico`、`woff`、`woff2`、`ttf`、`otf`、`eot`、`mp4`、`webm`、`mp3`、`ogg`、`wav`、`pdf` | 2592000（30 天） | 关 |

### 规则字段

| 字段 | API 字段 | 取值 | 默认值 | 作用 |
| --- | --- | --- | --- | --- |
| 条件类型 | 无 | 构建器 / 高级 | 构建器 | 见[请求条件](#请求条件) |
| 路径前缀 | `pathPrefixes` | 以 `/` 开头、不含空白、最长 1024 字符，逗号分隔，最多 32 个 | `/` | 构建器：请求路径以其中之一开头 |
| 后缀 | `extensions` | 1–16 位小写字母或数字（开头的 `.` 去掉），逗号分隔，最多 64 个 | 空 | 构建器：请求路径的扩展名为其中之一，例如 `css, js, png` |
| 表达式 | `expression` | `cache` 阶段的条件表达式，最长 16384 字符 | `true` | 高级：请求条件 |
| 动作 | `action` | 缓存 / 不缓存（`cache` / `bypass`） | 缓存 | 匹配后缓存或绕过缓存；「不缓存」时缓存时间、浏览器 TTL、遵循源站与过期内容字段不可用 |
| 缓存时间（秒） | `edgeTtlSeconds` | 0–31536000 | 3600 | 规则的缓存时间 |
| 浏览器 TTL（秒） | `browserTtlSeconds` | 0–31536000 | 空（「跟随源站」，API 为 0） | 见[浏览器 TTL](#浏览器-ttl) |
| 遵循源站 | `originCacheControl` | 开 / 关（`respect` / `override`） | 开 | 开：遵循源站 `Cache-Control` / `Expires`；关：覆盖源站缓存头 |
| 精确路径 | `paths` | 以 `/` 开头，最多 32 个 | 空 | 构建器：请求路径等于其中之一 |
| 状态码 | `statusCodes` | 100–599，最多 16 个 | 空 | 空：只缓存默认可缓存的状态码 |
| 最小（KB）/ 最大（KB） | `minSizeBytes` / `maxSizeBytes`（字节） | 不小于 0；最大不小于最小 | 空（「不限」，API 为 0） | 响应大小范围，1 KB 为 1024 字节 |
| 过期后后台更新（秒） | `staleWhileRevalidateSeconds` | 0–2592000 | 空（「关闭」） | stale-while-revalidate |
| 回源出错时用旧缓存（秒） | `staleIfErrorSeconds` | 0–2592000 | 空（「关闭」） | stale-if-error |
| 缓存带 Authorization 头的请求 | `cacheAuthorized` | 开 / 关 | 关 | 允许缓存带 `Authorization` 的请求，见 [Authorization](#authorization) |
| 缓存带 Set-Cookie 的响应 | `cacheSetCookie` | 开 / 关 | 关 | 允许缓存带 `Set-Cookie` 的响应，见 [Set-Cookie](#set-cookie) |

每个网站最多 64 条规则。没有规则时卡片显示「不缓存」，网站不缓存任何响应。保存前卡片按字段检查每条规则，不合格时提示「规则 {index}：{problem}」。

### 匹配

| 项目 | 行为 |
| --- | --- |
| 顺序 | 按列表顺序匹配，第一条适用的规则决定是否缓存、缓存时间和浏览器 TTL；没有适用规则时不缓存 |
| API 中的 `priority` | 0–10000，从小到大匹配，同一网站内不能重复（`CACHE_RULE_PRIORITY_DUPLICATE`）；不填时按列表位置取 10、20、30……；控制台保存时按列表位置重写 |
| 请求条件 | 一条表达式，按客户端原始请求求值：规范化后、规则改写前的路径，与缓存键、刷新一致 |
| 响应条件 | 状态码、响应大小。请求条件满足而响应条件不满足时，继续判断后续规则 |
| 响应大小 | 按 `Content-Length`；206 响应按 `Content-Range` 中的完整大小；大小未知时不满足大小条件 |
| 规则 ID | 内容不变的规则保存后保留原 ID；保存内容不变的规则不产生新版本 |

### 请求条件

请求条件是一条 `cache` 阶段的表达式，字段、函数与 IP 名单引用同[规则表达式](rules.md#表达式)，不能使用响应字段、`regex_replace` 与 `wildcard_replace`。`true` 匹配所有请求。

| 条件类型 | 行为 |
| --- | --- |
| 构建器 | 「路径前缀」「后缀」「精确路径」生成表达式：同一类条件中任一项满足即可，不同类条件都要满足，留空的条件不限制。例如前缀 `/static/, /img/` 与后缀 `css, js` 生成 `(starts_with(http.request.uri.path, "/static/") or starts_with(http.request.uri.path, "/img/")) and http.request.uri.path.extension in {"css" "js"}` |
| 高级 | 在「表达式」中直接编写，例如 `starts_with(http.request.uri.path, "/static/") and not ends_with(http.request.uri.path, ".html")`；表达式无效时「保存」不可用 |
| 切换 | 构建器形状的表达式可在两种类型间切换；其他表达式只能在「高级」中编辑（「构建器」不可用） |
| API | `expression` 为空时由 `pathPrefixes`、`paths`、`extensions` 生成；同时给出时三个列表须等于表达式的构建器形式。`sites.get` 返回 `expression`，构建器形状的规则同时返回三个列表 |
| 节点 | 构建器形状的条件（包括在「高级」中写成同样形状的表达式）以原来的结构化条件下发，旧节点照常执行；其他表达式需要节点能力 `rules-v2`，集群有活动节点不支持时构建器规则不能切换到「高级」 |
| 升级 | 升级前保存的缓存规则已改写为等价的构建器表达式，匹配结果不变 |

### 浏览器 TTL

「浏览器 TTL（秒）」大于 0 时，由该规则缓存的响应对访问者返回 `Cache-Control: max-age=N`。

| 项目 | 行为 |
| --- | --- |
| 生效条件 | 决定该响应的规则（与缓存时间相同）缓存它：覆盖模式且缓存时间大于 0，或遵循模式且源站的 `Cache-Control` 不含 `no-store`、`no-cache`、`private` |
| 作用 | 访问者收到的 `Cache-Control` 换成 `max-age=N`，缓存命中同样如此；边缘缓存的有效期仍按缓存时间 |
| 不生效时 | 访问者收到源站原来的 `Cache-Control` |
| 响应变换 | 响应变换规则仍可修改 `Cache-Control` |
| 节点要求 | `rules-v2`；集群有活动节点不支持时不能新设置（「集群中有节点不支持规则扩展」），已设置的值仍可修改或清除 |

### 缓存时间

| 模式 | 行为 |
| --- | --- |
| 覆盖（「遵循源站」关） | 使用规则的缓存时间，忽略源站的 `Cache-Control`、`Expires`（含 `no-store`、`private`）；未填状态码时只缓存 200、203、206、300、301、308。只用于不含用户数据的静态资源，否则登录用户的页面会返回给其他访客 |
| 遵循（「遵循源站」开） | 源站给出 `Cache-Control` 或 `Expires` 时按源站；两者都没有时使用规则的缓存时间；`Cache-Control` 未给出有效期时（例如只有 `public`）不缓存；`no-store`、`private` 生效 |
| 通用 | 带 `Set-Cookie` 的响应不缓存，规则打开「缓存带 Set-Cookie 的响应」时除外 |

### Authorization

带 `Authorization` 的请求默认绕过缓存，响应也不存入缓存（RFC 9111 §3.5），源站返回 `public` 或规则覆盖源站缓存头时同样如此。规则打开「缓存带 Authorization 头的请求」后按该规则缓存，此时持有任意凭据的访问者共用同一份缓存，只适合与凭据无关的内容。

### Set-Cookie

规则打开「缓存带 Set-Cookie 的响应」后，带 `Set-Cookie` 的响应按该规则缓存。

| 项目 | 行为 |
| --- | --- |
| 发给谁 | 只有本次回源的那个响应（`X-Cache` 为 `MISS`、`EXPIRED`、`BYPASS`）带 `Set-Cookie`，多行原样还原；`HIT`、`STALE`、`UPDATING`、`REVALIDATED` 的响应不带任何 `Set-Cookie`，其他访客收不到别人的 Cookie |
| 缓存对象 | 节点磁盘上的缓存对象保存着回源时的 `Set-Cookie`（只用于还原给那次请求），刷新或回收后删除 |
| 适用内容 | 源站对每个访客返回相同正文、只用 Cookie 标记会话的页面；正文因 Cookie 不同而不同时，把相关 Cookie 加入[缓存键](#缓存键与分片) |
| 节点要求 | `site-content-v1`；集群有活动节点不支持时只能关闭 |

### 过期内容

| 字段 | 行为 |
| --- | --- |
| 过期后后台更新（秒） | 对象过期后的该时长内先返回旧内容，同时在后台刷新 |
| 回源出错时用旧缓存（秒） | 对象过期后的该时长内，源站连接失败、超时或返回 5xx 时返回旧内容 |

两者在缓存时间为 0 时不生效。访问者收到的 `Cache-Control` 是源站原来的值，源站没有发送时不添加；设置了[浏览器 TTL](#浏览器-ttl) 时除外。

## 缓存键与分片

「缓存键与分片」卡片单独保存，对网站的全部规则生效。

| 字段 | API 字段 | 取值 | 默认值 | 作用 |
| --- | --- | --- | --- | --- |
| 查询参数 | `cacheKey.query` | 全部参与 / 全部忽略 / 仅指定参数 / 排除指定参数（`all` / `ignore` / `include` / `exclude`） | 全部参与 | 查询字符串如何进入缓存键 |
| 参数 | `cacheKey.queryParams` | 参数名（1–128 字符，不含空白、`&`、`=`、`#`），逗号分隔，最多 32 个；「仅指定参数」「排除指定参数」时必填 | 空 | 「仅指定参数」时保留的参数；「排除指定参数」时去掉的参数，名称可以以 `*` 结尾匹配前缀（`utm_*`） |
| 参数排序 | `cacheKey.sortQuery` | 开 / 关 | 关 | 排序后 `?a=1&b=2` 与 `?b=2&a=1` 命中同一对象；「全部忽略」时不可用 |
| 请求头 | `cacheKey.headers` | 头名称（RFC 7230 token，1–64 字符，保存为小写），逗号分隔，最多 8 个，不能是 `Cookie`、`Host` | 空 | 这些请求头的值不同则分别缓存 |
| Cookie | `cacheKey.cookies` | Cookie 名（RFC 7230 token，1–64 字符），逗号分隔，最多 8 个 | 空 | 这些 Cookie 的值不同则分别缓存。名称区分大小写；请求中同名 Cookie 出现多次、以其他大小写或百分号编码出现，或写在逗号之后时，源站可能取到另一个值，这样的请求不缓存 |
| 区分移动端与桌面端 | `cacheKey.deviceType` | 开 / 关 | 关 | 按 User-Agent 区分移动端（含平板）与桌面端 |
| 包含 Host | `cacheKey.includeHost` | 开 / 关 | 开 | 关闭后网站的全部域名共用缓存对象 |
| Range 分片回源 | `rangeSlice` | 开 / 关 | 关 | 可缓存的 `GET`/`HEAD` 按 1 MiB 分片回源和缓存，Range 请求只需命中涉及的分片；源站须支持 Range（返回 206）。关闭时 Range 请求先回源完整对象 |

| 项目 | 行为 |
| --- | --- |
| 固定组成 | 协议和缓存代数始终在缓存键中；关闭「包含 Host」后 HTTP 与 HTTPS 仍分别缓存 |
| 移动端识别 | User-Agent 匹配 `Mobi\|Android\|iPhone\|iPad\|iPod\|Windows Phone\|BlackBerry\|Opera Mini\|webOS` |
| 排除指定参数 | 参数名区分大小写，按原样和百分号解码后各比较一次；`*` 只能出现在名称末尾。「仅指定参数」中 `*` 是普通字符。源站仍收到完整的查询字符串；URL 刷新按同样规则比较查询 |
| 修改后 | 按旧键缓存的对象不再命中，由缓存区按不活跃时间回收 |
| 节点要求 | 「排除指定参数」需要 `site-content-v1`；集群有活动节点不支持时选项中不出现（已保存的仍保留） |

## PURGE 方法

「缓存」页签的「PURGE 方法」卡片：打开「启用」，在「PURGE 密钥」填写 16–256 个可打印 ASCII 字符（不含空格），或点击「生成」得到 32 字节随机密钥（base64url，显示「密钥仅显示一次，请在保存前复制」与复制按钮），然后保存。之后：

```bash
curl -X PURGE -H 'X-Purge-Key: <密钥>' -H 'Host: www.example.com' 'http://<节点 IP>/static/app.js?v=2'
```

返回 `202 {"task_id":"…"}`：控制台为该 URL 创建一个 URL 刷新任务，下发给网站所在集群的每个已启用节点，**刷新预热** 中来源显示「PURGE 方法（{node}）」。

| 项目 | 行为 |
| --- | --- |
| API 字段 | `cacheSettings.purgeMethod`：`enabled`、`key`（只写，省略时保留已保存的密钥）；`sites.get` 只返回 `enabled` 与 `keySet` |
| 密钥 | 只写：保存后显示「已保存，留空不修改」；填写新密钥即轮换。用主密钥信封加密入库，经节点通道下发给 agent，不进入数据面。启用时没有已保存的密钥返回 `PURGE_KEY_REQUIRED` |
| 应答 | 202 任务已创建；403 密钥错误或缺失（`purge-key-invalid`）；400 URL 无效或超过 2048 字符（`purge-url-invalid`）；429 超过速率（`purge-rate-limited`，带 `Retry-After`）；503 节点 agent 或控制台不可用（`purge-unavailable`）。应答为 JSON，`Cache-Control: no-store` |
| 速率 | 每个节点上，每个网站每个客户端网络（IPv4 地址，IPv6 按 /64）每秒 20 次，密钥正确的请求每个网站每秒 20 次（没有密钥的客户端只用完自己的额度）；控制台每个网站每分钟 120 个 PURGE 任务 |
| 范围 | 请求的 Host、路径与查询，不区分协议，比较规则同 URL 刷新；只刷新本网站 |
| 未启用 | `PURGE` 请求照常回源 |
| 审计 | `cache.purge`，操作者为节点，元数据 `method: PURGE` |
| 节点要求 | `site-content-v1`；集群有活动节点不支持时，未启用的卡片不可用 |

## 开发模式

网站「缓存」页签顶部的「开发模式」卡片打开「绕过缓存 3 小时」后，边缘节点在 3 小时内既不从缓存返回这个网站的请求，也不写入缓存：请求都回源，`X-Cache` 为 `BYPASS`，改动立即可见。卡片显示剩余时间，可随时关闭；网站页头与网站列表在开启期间显示「开发模式」标记。

| 项目 | 说明 |
| --- | --- |
| 时长 | 固定 3 小时；开启期间再开不会延长，需要时先关闭再开启 |
| 到期 | 节点按自己的时钟在到期时刻自动恢复缓存，不依赖控制台；控制台在一分钟内关闭它、发布并审计（控制台停机期间到期也一样，恢复后补记） |
| 已缓存内容 | 不清除。结束后节点继续使用开启前缓存的内容；需要新版本时另行[刷新](#刷新与预热) |
| 刷新与 PURGE | 照常工作；预热请求同样回源，不写入缓存 |
| 缓存规则 | 不生效：边缘 TTL、浏览器 TTL、过期内容（stale-while-revalidate / stale-if-error）都不适用，源站出错时不会返回旧内容 |
| WebP / AVIF 转换 | 只作用于缓存的响应，开启期间不转换 |
| 其他 | 访问控制、规则、WAF、压缩、错误页照常 |
| 发布 | 开启、关闭与到期直接下发到所有节点，不经金丝雀；回滚不会恢复或结束它 |
| 审计 | `site.development_mode_on` / `_off`（操作者）、`site.development_mode_expire`（系统） |
| 接口 | `GET` / `PUT /api/v1/sites/{id}/development-mode`，`{ "enabled": true }` |
| 节点要求 | `development-mode-v1`；集群中有节点不支持时不能开启 |

需要长期绕过缓存时，用缓存规则（不缓存）代替。

## X-Cache

「X-Cache」卡片中关闭「向访客发送 X-Cache」（`cacheSettings.xCache`，默认开）后，网站的响应不带 `X-Cache`（缓存命中也是）；缓存行为不变。关闭需要 `site-content-v1`，重新打开不需要。

## 字符编码

「字符编码」卡片为文本响应补上 `Content-Type` 的 `charset` 参数，只改响应头，不转换正文。

| 字段 | API 字段（`contentSettings.charset.`） | 取值 | 默认值 | 作用 |
| --- | --- | --- | --- | --- |
| 编码 | `name` | 关闭 / utf-8 / gbk / gb18030 / gb2312 / big5 / iso-8859-1 / shift_jis / euc-kr（API：`off` 或编码名） | 关闭 | 添加的编码 |
| 强制替换 | `force` | 开 / 关 | 关 | 源站已给出 `charset` 时替换它；关闭时保留源站的。「编码」为关闭时不可用 |
| 大写 | `uppercase` | 开 / 关 | 关 | 以大写写出编码名，如 `charset=GBK`。「编码」为关闭时不可用 |

只作用于源站返回（含缓存命中）的 `text/*`、`application/javascript`、`application/json`、`application/xml` 响应；节点自己生成的响应（错误页、人机验证页、PURGE 应答）不变。需要 `site-content-v1`。

## 压缩

「缓存」页签的「压缩」卡片依次为 Zstandard、Brotli、Gzip 三组（「开启」「压缩级别」「最小压缩大小（字节）」「压缩内容类型」）与「最大压缩长度（字节）」。这些字段与网站的 HTTPS 设置存放在一起，经 `https.update`（`PUT /sites/{id}/https`）保存，卡片只提交压缩字段，不影响「HTTPS」页签未保存的修改。字段、默认值与协商规则见 [HTTPS 与证书](https.md#压缩)。

## 图片格式转换

「缓存」页签的「图片格式转换」卡片把被缓存的 JPEG 与 PNG 按访客的 `Accept` 转换为 WebP 或 AVIF，「格式转换节省」卡片显示节省的字节数。见[图片格式转换](image-convert.md)。

## 缓存区

**集群与节点** 页面「设置」页签的「缓存区」卡片设置集群每个节点的缓存区；节点详情的「缓存」可单独覆盖本节点的容量。

| 字段 | API | 取值 | 默认值 | 作用 |
| --- | --- | --- | --- | --- |
| 容量（GiB） | `clusters.setCache` 的 `maxSizeGb` | 1–65536 的整数 | 10 | 缓存区磁盘上限，超出时按最久未用回收 |
| 不活跃回收（天） | `clusters.setCache` 的 `inactiveDays` | 1–90 的整数 | 7 | 对象多久未被访问即回收 |
| 节点详情：容量（GiB） | `nodes.setCache` 的 `maxSizeGb` | 1–65536，留空跟随集群（API：`null`） | 空（占位「集群：{size} GiB」） | 本节点的容量 |

| 项目 | 行为 |
| --- | --- |
| 索引内存 | 按容量自动推算：每 160 MiB 容量 1 MiB，最少 16 MiB，最多 512 MiB（10 GiB 为 64 MiB） |
| 生效 | 保存后发布集群配置版本（原因 `cluster_cache_updated` 或 `node_cache_updated`）；节点重新加载 nginx，已有连接不中断（卡片提示「保存后节点重载 nginx，不中断已有连接」）；索引大小改变时节点从磁盘重新载入缓存索引，缓存文件保留。节点单独的容量只让该节点重载 |
| 用量 | 节点每 10 分钟（启动 1 分钟后第一次，节点参数 `--cache-usage-interval`）统计缓存目录的磁盘占用，随心跳上报；节点详情显示「已用 … / …」和「测量于 …」，尚未上报时显示「尚未上报」 |
| 审计 | `cluster.cache_update`、`node.cache_update` |
| 节点要求 | 集群设置不需要新能力；节点单独的容量与用量上报需要 `cache-zone-v1`，集群有活动节点不支持且本节点没有单独容量时，节点详情的容量不可用 |

## 刷新与预热

1. 打开 **刷新预热**（`/purge`）。
2. 选择「URL 刷新」「目录刷新」「Host 刷新」「标签刷新」「全站刷新」「URL 预热」或「站点地图预热」。
3. 按类型填写：

   | 类型 | 输入 |
   | --- | --- |
   | URL 刷新、目录刷新、URL 预热 | 「URL」或「目录」：每行一个 URL，右上角显示「条数 / 500」 |
   | Host 刷新 | 「Host」：每行一个，或用空格、逗号分隔 |
   | 标签刷新 | 「网站」：选择一个网站（网站超过 8 个时可搜索）；「缓存标签」：每行或用逗号分隔一个标签 |
   | 全站刷新 | 「网站」：勾选网站（超过 8 个时可搜索），显示「已选 {count} 个」 |
   | 站点地图预热 | 「站点地图 URL」与「最多 URL 数」 |

   预热类任务在「设备」中勾选「桌面端」「移动端」，至少一个。
4. 点击「提交」。提示「已提交」，任务展开在「任务」列表顶部。
5. 验证：展开任务后各节点状态为「成功」；刷新后下一次请求返回 `X-Cache: MISS`。

| 项目 | 行为 |
| --- | --- |
| 下发 | 任务下发到网站所在集群的每个已启用节点，逐节点显示结果；已停用的节点列为「已跳过」 |
| 多集群 | 几个集群的网站都服务一个 Host 时（[域名优先级](domains.md#优先级)），URL、目录与 Host 刷新下发到每个这样的集群；预热与站点地图预热只交给在全部集群的网站（含已停用的）中按优先级选出的网站所在的集群 |
| 停用的网站 | 不能刷新或预热（「网站已停用」） |
| 提交条件 | 内容为空或只有空白行、超过 500 条、预热没有勾选设备时「提交」不可用；标签刷新所选网站的集群有节点不支持时显示「集群中有节点不支持标签刷新」，「提交」不可用 |
| 任务列表 | 「任务」每页 20 个，最新的在前；有任务未完成时每 2 秒刷新；展开显示「目标」「节点」与每个节点的「成功 {succeeded} · 失败 {failed}」和原因；没有任务时显示「暂无任务」 |
| 来源 | 操作者名称；PURGE 方法创建的任务为「PURGE 方法（{node}）」；补发的整站刷新为「系统（补发整站刷新）」 |
| URL 参数 | `/purge?site=<网站 ID>` 只列出该网站的任务（「任务」旁显示网站名，点击 × 清除），并在全站刷新与标签刷新中预选该网站；`/purge?type=<类型>&urls=<URL>` 打开该类型并填好 URL（多个 URL 用 JSON 数组，如 `urls=["https://www.example.com/a","https://www.example.com/b"]`）；`type` 取 `url`、`prefix`、`host`、`tag`、`site`、`prefetch`、`sitemap` |
| 命令菜单 | ⌘K / Ctrl+K 的「刷新 URL…」打开本页（在网站页面时只列出该网站的任务） |
| 其他入口 | 访问日志、网站「统计」页签的热门 URL 与「攻击」页签的 Top 路径，在行右侧的「⋯」中提供「刷新 URL」：路径展开到网站的每个精确域名（不含泛域名、`.` 后缀与正则域名），确认「刷新 {count} 个 URL？」后创建 URL 刷新任务，提示中的「查看任务」打开该网站的任务 |

### 在网站内刷新

网站「缓存」页签顶部的「刷新缓存」卡片：

1. 选择「URL 刷新」「目录刷新」或「全站刷新」。
2. URL 与目录刷新：在「路径或 URL」中每行填写一个以 `/` 开头的路径或完整 URL。路径展开到网站的每个精确域名（例如 `/app.js` 对 `www.example.com` 与 `example.com` 各一条），右上角显示展开后的 URL 数。有既不是路径也不是 URL 的行时提示「不是路径或 URL：…」，超过 500 条时提示「最多 500 个 URL」，网站只有泛域名、`.` 后缀或正则域名而填写了路径时提示「网站没有精确域名，请填写完整 URL」；这些情况下「提交」不可用。全站刷新显示将要刷新的域名。
3. 点击「提交」。

卡片下方列出该网站最近 5 个任务，节点执行期间每 2 秒刷新；「查看任务」打开 `/purge?site=<网站 ID>`。

### 任务类型

| 类型 | API `type` | 输入 | 行为 |
| --- | --- | --- | --- |
| URL 刷新 | `url` | 完整 URL，可带查询 | 刷新该 URL 的设备、请求头、Cookie 和分片变体，不区分协议。查询和 Host 按网站的缓存键规则比较，只刷新查询规范化后相同的对象；查询按百分号解码后比较（`?q=%3Cb%3E` 与 `?q=<b>` 相同）。路径按节点规范化后的形式比较（解码百分号编码、合并连续斜杠、处理 `.` 和 `..`），`/%73tatic/a.js` 与 `/static/a.js` 相同 |
| 目录刷新 | `prefix` | 不带查询的 URL 前缀 | 刷新该 Host 下路径以该前缀开头的全部对象；前缀按同样规则规范化后按字符串前缀比较；「包含 Host」关闭时不比较 Host |
| Host 刷新 | `host` | Host 名，不带端口，不能是泛域名 | 刷新该 Host 的全部对象，等同于该 Host 的 `/` 目录刷新；「包含 Host」关闭的网站刷新全部域名共用的对象 |
| 标签刷新 | `tag` | API：1–100 个网站与 1–500 个缓存标签；控制台每次一个网站 | 刷新这些网站中响应带有任一标签的对象，见 [Cache-Tag](#cache-tag) |
| 全站刷新 | `site` | 1–100 个网站 | 刷新网站的全部缓存 |
| URL 预热 | `prefetch` | 完整 `http://` 或 `https://` URL；设备 | 节点经本机专用的本地边缘监听像普通请求一样取回并缓存，按浏览器的 `Accept-Encoding` 请求；封禁、CC、挑战与拒绝类规则不作用于预热，预热也不计入统计。状态码小于 400 为成功；源站的跳转原样缓存、不跟随。缓存键含协议、不含端口（同一网站各[监听端口](https.md#网站端口)共用缓存对象，带端口的刷新与预热 URL 按网站处理，端口不影响结果）：有证书的网站，`http://` URL 同时预热 `https://` 形式；节点自身因「强制 HTTPS」返回的跳转改为预热 `https://` 形式，节点自身的其他跳转记为失败。网站开启「区分移动端与桌面端」时，勾选的每种设备各请求一次（移动端使用移动端 User-Agent），否则只请求一次 |
| 站点地图预热 | `sitemap` | 一个站点地图 URL、最多 URL 数（1–10000，默认 1000）；设备 | 节点经本机边缘层取回站点地图（因此遵守源站地址策略，控制台不对外请求），预热其中本网站的 URL，见[站点地图](#站点地图) |

URL 必须以 `http://` 或 `https://` 开头，不能包含账号，Host 必须由某个网站服务（按[域名优先级](domains.md#优先级)，含泛域名、`.` 后缀与正则域名匹配的主机），不能是 `*.example.com` 这样的模式。`https://` URL 在节点有 HTTPS 监听时经本地 TLS 监听预热（不校验本机证书）；没有 HTTPS 监听时失败（「节点无 HTTPS 监听」）。节点另有刷新专用的拉取通道：刷新不等前面已经开始的预热或升级。

### Cache-Tag

源站在响应头 `Cache-Tag` 中用逗号分隔列出标签，例如 `Cache-Tag: product-42, category-7`。

| 项目 | 行为 |
| --- | --- |
| 解析 | 去掉首尾空格与制表符后按小写比较；只接受可打印 ASCII（不含逗号）；单个标签最长 128 字节，整个响应头最长 4096 字节（多行时合并），超出的标签丢弃，响应照常缓存 |
| 转发 | 默认不转发给访问者（缓存命中也是）；在网站「缓存」页签的「Cache-Tag」卡片打开「向客户端转发 Cache-Tag」（`cacheSettings.keepCacheTag`）后原样转发。节点在两种情况下都记录标签 |
| 刷新结果 | 任务成功后，每个节点都不再返回带有已刷新标签的对象，包括过期后作为旧内容（stale）返回；分片缓存的对象全部分片一起刷新 |
| 索引 | 节点为用过 `Cache-Tag` 的网站记录每个缓存对象的标签，存放在共享内存（节点参数 `--tag-dict-mb`，默认 64 MiB），按最久未用淘汰 |
| 额外回源 | 索引中没有记录的对象（被淘汰、nginx 重启后、网站第一次返回 `Cache-Tag` 之前缓存的对象）在网站有标签刷新记录期间回源一次，之后正常命中 |
| 标签数量 | 每个任务最多 500 个标签；节点为每个网站保留最多 5000 个标签刷新记录（节点参数 `--purge-tags-per-site`），超出时合并为一次全站刷新 |
| 节点要求 | 节点能力 `purge-tag-v1`；集群有活动节点不支持时，Host 刷新与标签刷新被拒绝（`NODE_CAPABILITY_REQUIRED`，「节点尚不支持：Host 与标签刷新（{nodes}）」） |

### 站点地图

| 项目 | 行为 |
| --- | --- |
| 站点地图 URL | 必须属于一个网站，最长 2048 字符；节点从本机边缘层请求它，不跟随跳转，单个文档 30 秒、解压后最多 50 MiB，gzip 压缩的站点地图按内容识别 |
| 格式 | `urlset` 的 `<loc>`；`sitemapindex` 只展开一层，子站点地图也必须在该网站的域名上 |
| 筛选 | 只保留按[域名优先级](domains.md#优先级)由该网站服务的主机下的 `http(s)` URL，去重后按文档顺序截取前「最多 URL 数」个 |
| 结果 | 每个 URL 的每种设备计一次成功或失败；站点地图取不到或无法解析时失败（`sitemap_failed`），没有本网站的 URL 时失败（`sitemap_empty`） |
| 节点要求 | 节点能力 `prefetch-v2`（移动端预热同样需要）；集群有活动节点不支持时任务被拒绝（`NODE_CAPABILITY_REQUIRED`，「节点尚不支持：站点地图与多端预热（{nodes}）」） |

### 清除网站缓存

| 入口 | 操作 |
| --- | --- |
| 网站页面 | 标题栏的「⋯」→「刷新缓存」，确认「刷新 {name} 的全部缓存？」 |
| 命令菜单 | ⌘K / Ctrl+K 搜索网站，选择「刷新缓存：{name}」 |
| 网站列表 | 勾选网站（最多 100 个）后批量操作栏的「刷新缓存」，确认「刷新 {count} 个网站的全部缓存？」 |

三者都与 **刷新预热** 的「全站刷新」相同：控制台创建一个全站刷新任务，下发到网站所在集群的每个已启用节点，不发布配置版本。提示「已提交整站刷新」，其中的「查看任务」打开 `/purge?site=<网站 ID>`（批量时打开 `/purge`）。已停用的网站不能刷新缓存。

### 任务限制

| 项目 | 限制 |
| --- | --- |
| 每个任务 | 最多 500 条 URL、500 个 Host 或 500 个标签，或 100 个网站；每条 URL 最长 2048 字符；站点地图预热每个任务一个站点地图 |
| 节点刷新标记 | 每个网站最多保留 1000 条 URL、目录和 Host 刷新标记（节点参数 `--purge-markers-per-site`）与 5000 条标签刷新标记（`--purge-tags-per-site`），超出时合并为一次全站刷新 |
| 执行顺序 | 节点先执行一批任务中的刷新，再执行预热 |
| 预热时间 | 一批任务（最多 10 个）共享 4 分钟预算（节点参数 `--prefetch-budget`），从节点拉取任务起计时；单个 URL 60 秒；并发 4；到时未完成的 URL 记为失败（`prefetch_timeout`） |
| 磁盘文件 | 刷新不删除磁盘文件：下一次请求使用新的缓存键回源，旧对象按缓存区的不活跃时间和容量上限回收 |

### 节点状态

| 状态 | 含义 |
| --- | --- |
| 等待中 | 节点尚未取走任务；节点离线时保持此状态 |
| 执行中 | 节点已取走任务；5 分钟内未回报结果时重新下发 |
| 成功 / 失败 | 节点回报的结果 |
| 已跳过 | 节点已停用，任务未下发（「节点已停用，未下发」，`node_disabled`），不计入进度；停用节点时其未完成的任务同样记为已跳过 |

| 情况 | 行为 |
| --- | --- |
| 7 天未执行 | 记为失败（「节点 7 天内没有执行」，`task_expired`） |
| 补发整站刷新 | 离线超过 7 天后重连、或停用后重新启用的节点，不再执行错过的刷新，改为对涉及的每个网站执行一次全站刷新：合并为一个任务，来源显示「系统（补发整站刷新）」，只发给该节点；已删除的网站不在其中。原任务在该节点下标记「节点重新连接时已补发整站刷新」 |
| 预热 | 错过的预热不补发 |
| 保留 | 任务保留 90 天；节点仍需补发整站刷新的刷新任务保留到补发之后 |

## API

路径相对于 `/api/v1`，认证与请求格式见 [API 与端点](../reference/api.md)。

| 过程 | 方法与路径 | 说明 |
| --- | --- | --- |
| `sites.get` | `GET /sites/{id}` | 返回 `origins`、`originSettings`、`cacheRules`、`cacheSettings`、`contentSettings`、`cacheGeneration`；不返回 S3 Secret Key 与 PURGE 密钥 |
| `sites.update` | `PATCH /sites/{id}` | 只修改给出的部分。`origins`、`cacheRules` 整体替换；`originSettings` 整体替换，省略的字段取默认值，`activeHealthCheck`、`sessionAffinity`、`protocol`、`grpc`、`tries`、`statusRetry`、`tlsTrust`、`clientCertificate` 省略时保持原值；`cacheSettings` 整体替换，`keepCacheTag`、`xCache`、`purgeMethod` 省略时保持原值；`contentSettings` 整体替换，`rulesBodyLimit` 省略时保持原值。返回网站与配置版本 |
| `sites.create` | `POST /sites` | 新建网站时一并给出 `origins`（必填）、`cacheRules`、`originSettings`、`cacheSettings`、`contentSettings` |
| `sites.originHealth` | `GET /sites/{id}/origin-health` | 每个源站的 `downNodes`、`onlineNodes`、最后一次错误（`lastError`、`lastErrorCode`、`lastErrorParams`）与每个节点按来源（`passive` / `active`）的结果 |
| `sites.originQuality` | `GET /sites/{id}/origins/quality` | `range`：`1h`、`6h`、`24h`（默认）、`7d`、`30d`；`unsupportedNodes` 为缺少 `origin-stats-v1` 的活动节点数 |
| `sites.features` | `GET /sites/{id}/features` | 网站所在集群当前能否开启各项依赖节点能力的功能 |
| `sites.purgeAll` | `POST /sites/{id}/purge` | 全站刷新，等同 `cacheTasks.create` 的 `{"type":"site","siteIds":["<网站 ID>"]}`，返回任务 |
| `cacheTasks.create` | `POST /cache-tasks` | 201，返回任务。字段 `type`、`urls`、`siteIds`、`hosts`、`tags`、`variants`（`desktop` / `mobile`，默认 `["desktop"]`）、`maxUrls`；审计 `cache.purge` 或 `cache.prefetch` |
| `cacheTasks.list` | `GET /cache-tasks` | `siteId`（可选）、`page`、`pageSize`（1–100，默认 20） |
| `cacheTasks.get` | `GET /cache-tasks/{id}` | 单个任务与每个节点的结果 |
| `https.get`、`https.update` | `GET`、`PUT /sites/{id}/https` | 压缩字段与 HTTPS 设置一起读写，见 [HTTPS 与证书](https.md#压缩) |
| `imageConvert.get`、`imageConvert.update`、`imageConvert.savings` | `GET`、`PUT /sites/{id}/image-convert`；`GET /sites/{id}/image-convert/savings` | 见[图片格式转换](image-convert.md#api) |
| `clusters.setCache` | `PUT /clusters/{id}/cache` | `maxSizeGb`、`inactiveDays`；发布集群 |
| `nodes.setCache` | `PUT /nodes/{id}/cache` | `maxSizeGb`，`null` 跟随集群；发布集群 |

服务账号不能调用以上过程（`sites.get` 除外，需要 `sites:read`）。

## 限制

| 项目 | 说明 |
| --- | --- |
| 数量 | 每个网站 1–50 个域名、1–32 个源站、最多 64 条缓存规则 |
| 缓存规则条件 | 最长 16384 字符；不能读取响应字段 |
| 源站组 | 缓存键不含源站组 |
| 缓存区 | 每个节点一个缓存区；容量与不活跃时间按集群设置，节点只能覆盖容量 |
| 最大压缩长度 | 只对长度已知的响应生效；分块（长度未知）的响应照常压缩 |
| HTTPS 预热 | 需要节点有 HTTPS 监听，即集群里至少有一个网站配置了证书；缓存键包含协议，`http://` 预热只填充 HTTP 访问的缓存 |
| 设备变体 | 只区分桌面端与移动端（平板按移动端处理） |
| Authorization 开关 | 需要节点 proto v0.2.1 及以上；更早的节点忽略「缓存带 Authorization 头的请求」 |
| WebSocket | 只识别 `Upgrade: websocket` |
| HTTP/2 回源 | 不回退到 HTTP/1.1；不发送 `:authority` |
| gRPC 健康检查 | 只调用 `Check`，不使用 `Watch`；不支持 gRPC 反射或自定义方法 |
| PROXY protocol | 只针对 TCP：HTTP/3 访问者在头中也报为 TCP；访问者的真实 IP 取自请求头时（[可信代理报头](../deploy/nodes.md#访客-ip)）源端口为 0；S3 源站不可用 |

## 故障排查

节点自身返回的错误带响应头 `X-Edgeweir-Error` 和 `Cache-Control: no-store`。`X-Cache` 为 nginx 缓存状态：`MISS`、`HIT`、`BYPASS`、`EXPIRED`、`STALE`、`UPDATING`、`REVALIDATED`。

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 保存提示「源站地址 … 属于特殊用途地址段 …，不在源站地址允许清单中」（`ORIGIN_ADDRESS_FORBIDDEN`） | 源站 IP 字面量在特殊用途地址段 | 改用公网地址，或把地址段加入源站地址允许清单 |
| 源站显示「… 是特殊用途地址，不在源站地址允许清单内」 | 源站域名的解析结果全部为特殊用途地址 | 同上 |
| 502，`X-Edgeweir-Error: origin-unreachable` | 最后一次尝试没有得到源站的响应头：连接失败、TLS 失败或源站断开 | 查看「源站」卡片的错误与「回源质量」；检查源站与防火墙 |
| 504，`X-Edgeweir-Error: origin-timeout` | 最后一次尝试超过「超时（秒）」 | 检查源站响应时间，或调大「连接」「读取」超时 |
| HTTPS 源站返回 502，源站显示「TLS 握手或证书校验失败」 | 源站证书自签名、不覆盖 SNI 或证书链不完整；节点缺少 CA 文件 | 换受信任证书或填写正确的「SNI」；自签名源站关闭「校验源站证书」或改用 Origin CA；节点用 `--trusted-ca` 指定 CA 文件 |
| 502，`X-Edgeweir-Error: no-origin` | 所有源站都在尝试前被剔除（解析失败、地址被禁止、缺少 S3 凭据） | 查看「源站」卡片的错误信息 |
| 502，`X-Edgeweir-Error: origin-signing` | 节点无法为 S3 源站的请求计算签名（节点日志 `cannot sign origin request`） | 查看节点日志；检查「区域」「Access Key ID」「Secret Key」 |
| 404，`X-Edgeweir-Error: unknown-host` | Host 不属于节点已应用的任何网站，也不是已停用网站的域名：网站或域名已删除，或节点未应用最新版本 | 检查域名与节点「已应用版本」 |
| 503，`X-Edgeweir-Error: site-disabled` | 网站已停用 | 在网站「概览」页签启用网站 |
| HTTPS 请求在 TLS 握手时失败 | SNI 不属于节点正在服务的网站（未知域名、已停用的网站），或网站没有证书 | 用 HTTP 请求查看节点的应答；为网站配置证书，见[HTTPS 与证书](https.md) |
| 508，`X-Edgeweir-Error: loop-detected` | 源站指回了本节点或其上游 CDN | 修改源站地址 |
| 403，`X-Edgeweir-Error: websocket-disabled` | 网站关闭了 WebSocket | 打开「WebSocket」 |
| 「回源 Host」下方提示「填写域名或 IP，可带端口；IPv6 带端口时加方括号」，或保存提示「回源 Host 无效：…」（`ORIGIN_HOST_HEADER_INVALID`） | 含空格、引号、`/`、`\`，带协议或路径，或是不带端口的方括号 IPv6 | 只填主机名或 IP，可带端口 |
| 源站显示「回源 Host 无效，节点会跳过该源站」 | 旧版本控制台保存了节点不接受的回源 Host；节点跳过该源站，网站只有这一个源站时不下发 | 修改「回源 Host」后保存 |
| 保存提示「请填写 … 的 Secret Key」（`S3_SECRET_REQUIRED`） | 新的 Access Key ID 没有填写 Secret Key | 填写「Secret Key」 |
| 保存提示「S3 源站不支持 PROXY protocol」（`ORIGIN_PROXY_PROTOCOL_S3`） | API 为 S3 源站设置了 `proxyProtocolVersion` | 设为 0 |
| 保存提示「信任 Origin CA 需要先开启校验源站证书」「S3 源站不能用 Origin CA 校验」「请先创建 Origin CA（证书 → 源站证书）」 | 「信任」为 Origin CA 时的前提不满足 | 打开「校验源站证书」；移除 S3 源站或改回系统 CA；创建 Origin CA，见[源站保护](https.md#源站保护) |
| 保存提示「请先创建回源客户端 CA（证书 → 回源客户端）」（`ORIGIN_CLIENT_CA_NOT_FOUND`） | 打开「出示客户端证书」而回源客户端 CA 未创建 | 创建回源客户端 CA，见[源站保护](https.md#源站保护) |
| 保存提示「gRPC 需要以 HTTP/2 回源」（`ORIGIN_GRPC_REQUIRES_HTTP2`） | API 在「回源 HTTP 版本」不是 HTTP/2 时打开了 gRPC | 同时把 `protocol` 设为 `http2`，或关闭 `grpc` |
| 改为 HTTP/2 后 502，源站显示「TLS 握手或证书校验失败」 | HTTPS 源站不支持 HTTP/2（ALPN 没有 `h2`） | 在源站开启 HTTP/2，或改回 HTTP/1.1 |
| 改为 HTTP/2 后 502，源站显示「无法连接源站」 | HTTP 源站不接受 h2c | 同上 |
| 回源 HTTP/1.1 时客户端收到无法解析的响应或 502 | 源站只接受 HTTP/2（例如以 h2c 监听的 gRPC 服务） | 把「回源 HTTP 版本」改为 HTTP/2 |
| gRPC 客户端收到 421 | 客户端以 h2c 访问了未打开 gRPC 的网站的域名 | 在该网站打开「gRPC」，或改用 HTTPS |
| gRPC 客户端报告缺少 trailers | 网站没有打开「gRPC」，请求按普通请求回源 | 打开「gRPC」 |
| 405，`X-Edgeweir-Error: method-not-allowed` | S3 源站只接收 `GET`、`HEAD` | 为写请求增加非 S3 源站 |
| 带 `Authorization` 的请求始终 `X-Cache: BYPASS` | 默认绕过缓存 | 在对应规则打开「缓存带 Authorization 头的请求」 |
| 响应始终 `X-Cache: BYPASS` | 没有适用的缓存规则，或适用的都是「不缓存」规则 | 检查规则顺序与条件 |
| 响应始终 `X-Cache: MISS` | 遵循源站模式下源站未给出有效期；响应带 `Set-Cookie` 而规则没有打开「缓存带 Set-Cookie 的响应」；缓存时间为 0 | 检查规则和源站响应头 |
| 响应没有 `X-Cache` | 网站关闭了「向访客发送 X-Cache」 | 在「X-Cache」卡片打开 |
| 保存缓存规则提示「规则 {index}：…」 | 该规则的字段不符合取值范围 | 按提示修改该规则 |
| 保存缓存规则提示「两条缓存规则的优先级都是 …」（`CACHE_RULE_PRIORITY_DUPLICATE`） | API 给出了重复的 `priority` | 使用不同的 `priority`，或省略 |
| 413，`X-Edgeweir-Error: body-too-large` | 请求体（`Content-Length`，或没有时读到的大小）超过网站或规则的请求体上限 | 调高「请求体上限」，或为上传路径加配置规则 |
| `PURGE` 返回 403，`purge-key-invalid` | `X-Purge-Key` 缺失或与保存的密钥不同 | 检查密钥；忘记时生成新密钥并保存 |
| `PURGE` 返回 429，`purge-rate-limited` | 同一客户端网络超过每秒 20 次、网站的有效请求超过每秒 20 次，或超过每分钟 120 个任务 | 按 `Retry-After` 稍后再试；批量刷新用 **刷新预热** 或 API |
| `PURGE` 返回 503，`purge-unavailable` | 节点 agent 或控制台不可达 | 检查节点与控制台的连接 |
| `PURGE` 请求被转发到源站 | 网站没有启用 PURGE 方法 | 在「PURGE 方法」卡片启用 |
| 保存提示「开启 PURGE 方法需要先设置密钥」（`PURGE_KEY_REQUIRED`） | 启用时没有保存过密钥 | 填写或生成密钥后保存 |
| 源站的 502 直接返回访问者，没有换源站重试 | 关闭了「源站返回 502 / 503 / 504 时重试」，或「尝试次数」为 1 | 检查「源站池设置」 |
| 开关或字段不可用，显示「集群中有节点不支持」 | 集群有活动节点缺少该功能需要的节点能力（见[源站池设置](#源站池设置)与各节的节点要求） | 升级节点，见[节点升级](node-upgrades.md) |
| 「源站」卡片显示「至少保留一个默认组源站」 | 所有源站都填写了「源站组」 | 清空至少一个源站的「源站组」 |
| 保存源站或缓存规则提示「规则无效」（`RULE_INVALID`） | 移除了仍被「源站覆盖」规则选择的源站组；缓存规则条件无效 | 先修改规则，或保留该组的源站；修正条件 |
| 保存缓存规则提示「IP 名单不存在：…」（`IP_LIST_REFERENCE_UNKNOWN`） | 条件引用了不存在的 IP 名单 | 创建该名单或修改条件，见[规则](rules.md) |
| 「节点尚不支持：…（<节点>）」（`NODE_CAPABILITY_REQUIRED`） | 服务账号或后台任务发布的配置、或刷新预热任务，需要集群活动节点缺少的节点能力（如「规则扩展」「HTTP/2 与 gRPC 回源」「Host 与标签刷新」「站点地图与多端预热」） | 升级节点，见[节点升级](node-upgrades.md) |
| 选择了不同源站组的请求返回同一个缓存对象 | 缓存键不含源站组 | 按路径选择源站组，或把选择依据加入缓存键 |
| 「没有网站使用 …」（`CACHE_TASK_HOST_UNKNOWN`） | URL 的 Host 不是任何网站的域名；PURGE 方法请求的 Host 不属于该网站 | 检查域名拼写 |
| 「网站已停用」（`SITE_DISABLED`） | 任务或「刷新缓存」涉及已停用的网站 | 在网站「概览」页签启用网站后再提交 |
| 「URL 无效：…」（`CACHE_TASK_URL_INVALID`） | 不是 `http(s)` URL、包含账号，或目录刷新带查询 | 修正 URL |
| 「Host 无效：…」（`CACHE_TASK_HOST_INVALID`） | 带端口、泛域名或不是合法主机名 | 每行填写一个主机名 |
| 「缓存标签无效：…」（`CACHE_TASK_TAG_INVALID`） | 标签含逗号、非 ASCII 字符或超过 128 字节 | 修正标签；源站的 `Cache-Tag` 使用同样的规则 |
| 标签刷新显示「集群中有节点不支持标签刷新」 | 所选网站的集群有活动节点缺少 `purge-tag-v1` | 升级节点 |
| 预热失败，原因「节点无 HTTPS 监听」 | 集群里没有配置了证书的网站，节点只有 HTTP 监听 | 改用 `http://` URL，或为网站配置证书 |
| 「站点地图 … 获取失败（…）」 | 站点地图返回错误状态码或跳转、超时、超过 50 MiB（「解压后超过 50 MiB」）或不是有效的站点地图（「不是有效的站点地图」） | 直接请求站点地图 URL 检查；跳转时填写最终地址 |
| 「站点地图 … 中没有本网站的 URL」 | 站点地图只列出了其他域名的 URL | 检查站点地图中的域名 |
| 标签刷新后仍是旧内容 | 源站没有在该对象的响应中发送对应的 `Cache-Tag`，或标签含不接受的字符 | 打开「向客户端转发 Cache-Tag」后查看响应头 |
| 「预热超时，已完成 …」 | 超过 4 分钟预算 | 拆分为多个任务 |
| 「节点不支持此任务类型（…），请升级 edgeweir-node」 | 节点版本过旧 | 升级节点，见[节点升级](node-upgrades.md) |
